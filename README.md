# MIG_mose

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
![Checks status badge](https://github.com/decarbon1ze/migmose/workflows/checks/badge.svg)

MIG_mose generates machine-readable files from MIG `.docx` documents ([edi-energy](https://www.edi-energy.de/index.php?id=38)).
MIG_mose is the sister of [kohlrahbi](https://github.com/Hochfrequenz/kohlrahbi).

> [!NOTE]
> This repository is a fork of [Hochfrequenz/migmose](https://github.com/Hochfrequenz/migmose), which Hochfrequenz no longer maintains.
> decarbon1ze maintains this fork. It writes the same files as the original for the same documents.
> The package on PyPI is the original; install the fork from this repository (see [Installation](#installation)).

## Tech-Stack
- MIG_mose is a Python (3.11, 3.12, 3.13) project, managed with [uv](https://docs.astral.sh/uv/).
- .docx files a processed by the [python-docx](https://python-docx.readthedocs.io/en/latest/) library.
- EdiFact formats are used as in [efoli](https://github.com/Hochfrequenz/efoli)).
- syrupy for unittest snapshots

## Installation
Install MIG_mose from this repository, for example as a tool with [uv](https://docs.astral.sh/uv/):

```bash
uv tool install git+https://github.com/decarbon1ze/migmose
```

or into the current environment with pip:

```bash
pip install git+https://github.com/decarbon1ze/migmose
```

## Features And How To Use Them

At this point, MIG_mose works as a command-line interface tool (CLI).
There are several flags available to provide a user-friendly way to interact with MIG_mose.
Below the available options are listed:

- **Input Directory (`-eemp`, `--edi-energy-mirror-path`):**
    - Description: This option allows the user to specify the path to a edi-energy-mirror-like repository which contains .docx files for the MIGs (Message Implementation Guides) in subdirectories structured by the format version.
    - Example: `--edi-energy-mirror-path /path/to/edi_energy_mirror`

- **Message Format (`-mf`, `--message-format`):**
    - Description: This option defines the set of message formats to be parsed. Users can specify multiple message formats by providing multiple values. The formats are EdiFact formats (cf. [efoli.EdifactFormat](https://github.com/Hochfrequenz/efoli/blob/src/efoli/edifact_format.py)). If no format is specified, all formats are parsed.
    - Example: `--message_format "UTILMD" --message_format "ORDCHG"`

- **Output Directory (`-o`, `--output-dir`):**
    - Description: This option allows the user to specify the path to the directory which should contain the output files generated by the tool. If the directory does not exist, it will be created automatically.
    - Example: `--output_dir /path/to/output_directory`
- **Output File Type (`-ft`, `--file-type`):**
    - Description: Defines the output format. Without this option MIG_mose writes `csv`, `nested_json`, `reduced_nested_json` and `tree`. Choose between:
      - `csv` for flat Nachrichtenstruktur tables
      - `nested_json` for json files of the nested Nachrichtenstruktur tables
      - `reduced_nested_json` for a reduced nested Nachrichtenstruktur
      - `tree` for .tree files (cf. [MAUS tree](https://github.com/Hochfrequenz/mig_ahb_utility_stack/blob/5cce94069ead5aa63d4b9ac7f5e0fcec0bf608ea/src/maus/reader/tree_to_sgh.py))
      - `segmentlayout_json` for the segment layouts: the data elements of each segment (see [Segment layouts](#segment-layouts))
    - Example: `--file-type "csv"
- **Format Version (`-fv`, `--format-version`):**
    - Description: Defines the format version.
    - Example: `--format-version "FV2310"

### Usage Example

To use the CLI logic provided by this tool, follow the command syntax below:

```bash
migmose -eemp /path/to/edi_energy_mirror -o /path/to/output_directory -mf "UTILMD" -mf "ORDCHG" -ft "csv" -fv "FV2310"
```

### Segment layouts

A MIG describes each segment in a table of its own, the segment layout: the data elements of the segment, the data element groups (composites) that bundle them, their status and format in the standard and in the BDEW profile, and the column "Anwendung / Bemerkung", which also lists the codes.

`--file-type segmentlayout_json` writes them to `segmentlayouts.json`, one entry per segment in the order of the document:

```json
{
    "segmentlayouts": [
        {
            "zaehler": "0160",
            "nr": "00007",
            "bezeichnung": "NAD",
            "elemente": [
                {
                    "bezeichnung": "3035",
                    "name": "Beteiligter, Qualifier",
                    "standard_status": "M",
                    "standard_format": "an..3",
                    "bdew_status": "M",
                    "bdew_format": "an..3",
                    "anwendung": "\tMS\tDokumenten-/Nachrichtenaussteller bzw. -\nabsender"
                },
                {
                    "bezeichnung": "C082",
                    "name": "Identifikation des Beteiligten",
                    "standard_status": "C",
                    "bdew_status": "R",
                    "anwendung": "",
                    "datenelemente": [
                        {
                            "bezeichnung": "3039",
                            "name": "Beteiligter, Identifikation",
                            "standard_status": "M",
                            "standard_format": "an..35",
                            "bdew_status": "M",
                            "bdew_format": "an..35",
                            "anwendung": "MP-ID"
                        }
                    ]
                }
            ]
        }
    ]
}
```

- `nr` is the number of the segment in the Nachrichtenstruktur, so it connects a layout with the line of the segment in the other files.
- An entry of `elemente` with `datenelemente` is a data element group, any other a data element of the segment itself.
- `name` and `anwendung` are the texts of the document, with its line breaks and tabs. MIG_mose does not split `anwendung` into codes.

## Development

### Setup

[uv](https://docs.astral.sh/uv/) installs Python, the dependencies and the development tools in the versions `uv.lock` pins:

```bash
uv sync
```

### Run all tests and linters

```bash
uv run pytest               # tests
uv run ruff check           # linter
uv run ruff format --check  # formatting
uv run ty check             # type check
uv run codespell src README.md
```

To update the test snapshots run
```bash
uv run pytest --snapshot-update
```
